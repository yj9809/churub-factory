# v1.1.0 리팩터링 기록

## 목표

실제 출시 버전 1.0.1의 플레이 경험과 서버 스키마를 유지하면서 다음을 개선합니다.

- 공개 저장소 보안
- 직원 AI 작업 할당의 예측 가능성
- 핵심 로직의 테스트 가능성
- 저장 실패 시 안정성
- 포트폴리오 문서와 재현성

## 1. 저장소 보안과 위생

### 문제

- Android keystore가 버전 관리에 포함됨
- IDE 설정과 Unity 사용자별 레이아웃이 추적됨
- 이미 임포트된 대형 `.unitypackage`가 중복 보관됨

### 결정

- 서명 키 경로와 alias를 PlayerSettings에서 제거
- `Key/`, `*.keystore`, `*.jks`를 ignore
- `.idea/`, `UserSettings/`, 사용자 레이아웃 제거
- 런타임에 필요하지 않은 원본 `.unitypackage` 제거

과거 Git 기록에 포함된 키는 별도의 기록 정리와 키 교체 검토가 필요합니다.

## 2. 직원 작업 예약

### 기존 문제

- 직원마다 전체 작업 목록을 직접 순회
- 선택 직후 대상의 사용 상태를 `false`로 설정하여 예약이 성립하지 않음
- `StopCoroutine(CheckStack())`에 새 Enumerator를 전달하여 기존 코루틴을 중지하지 못함
- 다른 직원에게 `CheckStack` 코루틴을 반복 추가
- `Count >= 0` 조건이 항상 참이어서 거리와 무관하게 타깃 전환 가능

### 변경

- 순수 C# `WorkScheduler<T>` 도입
- 등록, 최고 재고 선택, 예약, 해제를 한 책임으로 캡슐화
- 직원별 코루틴 핸들을 보관해 하나만 실행
- 비활성화와 픽업 시 예약 해제
- EditMode 테스트 4개 추가

### 유지한 사항

- 기존 `Employee` 프리팹의 직렬화 필드
- `IStackable` 생산시설 계약
- NavMesh 이동 및 충돌 기반 아이템 전달
- 기존 애니메이션과 적재 연출

## 3. 서버 데이터 생성

### 기존 문제

데이터 삽입 실패 시 `GameDataInsert()`가 즉시 자기 자신을 호출했습니다. 장시간 장애가 발생하면 호출 스택이 계속 증가할 수 있습니다.

### 변경

- 최대 삽입 시도 횟수를 3회로 제한
- 성공 여부를 `bool`로 반환
- 실패 시 시도 횟수와 최종 오류 기록
- 삽입과 갱신의 Param 생성을 공통 메서드로 통합

### 호환성

백엔드 테이블 이름과 모든 필드 이름은 1.0.1과 동일하게 유지합니다.

## 검증 기록

- Unity: 2021.3.32f1
- 빌드 타깃: Android
- 스크립트 컴파일: 성공
- EditMode: 4 passed, 0 failed
- 순수 코어 .NET 8 smoke test: 성공
- Android 개발용 APK 빌드: 성공

수동 플레이와 Android 실기기 설치·실행 검증은 후속 단계에서 수행합니다.

## 4. 런타임 데이터 모델과 저장 스키마 경계

### 기존 문제

- UI, 플레이어, 시설 코드가 Dictionary의 문자열 키를 직접 사용
- 오타가 컴파일 단계에서 발견되지 않고 실행 중에만 실패
- 기본 밸런스 값과 백엔드 필드 이름이 `DataManager`에 함께 존재
- 골드/박스 업그레이드가 다음 비용 대신 업그레이드 횟수에 비용 값을 기록

### 변경

- Unity 비의존 `GameDataState`에 기본값과 타입 속성 이동
- `GameDataSchema`에서 테이블, 필드, 레거시 키를 단일 관리
- 런타임 소비 코드의 Dictionary 직접 접근 제거
- `BaseCost`는 기존 코드 호환을 위한 얇은 어댑터로 유지
- 상태 기본값과 레거시 Dictionary 양방향 호환을 검증하는 EditMode 테스트 5개 추가
- 골드/박스 업그레이드 비용 갱신 대상 수정

### 호환성

`TestUserData` 테이블 이름과 `upgradeCosts`, `playerData`, `employeeData`, `objectData`, `gameProgressBool`을 포함한 모든 저장 필드는 그대로 유지합니다. Core 스모크 테스트는 통과했으며, Unity EditMode 재실행은 현재 머신의 라이선스 IPC 오류 해결 후 필요합니다.

## 5. 업그레이드 서비스 분리

### 기존 문제

- `UIManager`가 구매 판정, 골드 차감, 능력치 계산, 단계·비용 증가까지 담당
- 6종 업그레이드 규칙이 하나의 큰 switch에 결합
- UI 없이 업그레이드 밸런스를 테스트하기 어려움
- 직원 생성 설정이 잘못되면 골드 차감 후 Unity 오브젝트 생성에서 실패할 수 있음

### 변경

- Unity 비의존 `UpgradeService` 도입
- `UpgradeType`, `UpgradeProgress`, `UpgradePurchaseResult`로 입력과 결과 명시
- 구매 전 `EvaluatePurchase`로 골드 부족, 최대 단계, 잘못된 상태 판정
- 성공한 경우에만 골드, 단계, 다음 비용, 능력치 갱신
- 직원 세 번째 구매는 포장 담당 생성이 필요하다는 결과만 Unity 계층에 전달
- `UIManager`는 입력과 텍스트·스프라이트·사운드 갱신만 처리
- 출시 버전의 5단계 비용·배율과 실패 시 무변경을 검증하는 EditMode 테스트 10개 추가

### 호환성

업그레이드 Dictionary 키, 초기 비용, 최대 단계, 속도 배율, 직원 최대 3명 규칙을 유지합니다. UI 버튼에 연결된 `Upgrade(int)` 시그니처도 유지하여 씬과 프리팹 이벤트 참조를 변경하지 않습니다.

순수 Core 스모크에서 6종 구매, 골드 부족, 직원 최대 인원과 세 번째 포장 담당 요청을 확인했습니다. Unity EditMode 전체 실행은 현재 머신의 라이선스 IPC 오류로 보류되어 있습니다.

## 6. 직원 생성 팩토리 분리

### 기존 문제

- `UIManager`가 생성 가능 여부 확인, 랜덤 프리팹 선택, `Instantiate`까지 수행
- 포장 담당의 `NavMeshAgent` 제거와 역할 설정이 UI 로직에 포함
- 사용 가능한 프리팹 목록 제거와 플레이어 직원 목록 등록도 UI가 담당
- 프리팹에 `Employee` 컴포넌트가 없는 구성 오류를 생성 전에 구분하지 못함

### 변경

- Unity 런타임 경계에 `EmployeeFactory` 도입
- 생성 가능한 프리팹만 후보로 선택하고, 성공 후 원본 목록에서 제거
- 일반 운반 직원과 포장 담당 직원의 생성·역할 설정을 캡슐화
- `EmployeeCreationStatus`로 프리팹, 컴포넌트, 포장 시설, 배치 지점 오류를 구분
- `UIManager`는 구매 순서 조정과 사용자 메시지 표시만 담당

### 호환성

`Upgrade(int)` 시그니처, 기존 직원 프리팹, 세 번째 직원을 포장 담당으로 생성하는 규칙을 유지합니다. 신규 `MonoBehaviour`나 씬 참조를 추가하지 않아 씬 설정을 변경할 필요가 없습니다.
